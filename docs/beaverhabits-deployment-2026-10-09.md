## Accounts, isolation and providers

Native email/password accounts are provisioned by the operator through the application's supported administrator registration API. Public registration is closed. This release has no configured OIDC connection to Utilibre's existing identity system. `TRUSTED_LOCAL_EMAIL` and `TRUSTED_EMAIL_HEADER` are empty. Native session JWTs last 24 hours; API tokens, if created, do not expire automatically and can be reset/deleted through `/gui/tokens`.

The retained service-administration identity is private operational configuration, not a published operator/contact identity. Its credentials and app secrets are root-private under `/opt/utilibre/beaverhabits/private`. Neither setup scripts nor source offers contain their values. No account email was sent. Email recovery, Google One Tap, Telegram automatic backup, Umami, Sentry, Highlight and subscription/plan integrations are disabled. Application resources load locally; the private two-browser test observed no external resource requests. Public HTTPS involves Cloudflare, the Caddy edge and Hetzner infrastructure, with their separate retention.

The app has only internal network 172.29.145.0/24; the fixed nginx gateway also uses ingress network 172.29.146.0/24. Host and forwarded egress from these subnets are denied. Private port 3216 permits the separate Caddy edge and a local verification binding; it is not an unrestricted LAN/public listener. The app is limited to 1.5 CPU/768 MiB/128 PIDs with a read-only root, non-root UID and dropped capabilities. The gateway has 0.5 CPU/96 MiB, 256 worker connections, 32 connections per IP, 2 MiB request bodies and 20 authentication requests/minute with burst five. One native worker preserves NiceGUI session affinity. These are configured limits, not measured user capacity.

## Data, exports and deletion

The server can read account emails/password hashes, habits, completion records, notes, settings and attached note images in SQLite. Native NiceGUI session files and the browser session cookie persist separately. No end-to-end encryption is claimed. Habit records are deliberately retained for the user's requested function, not used for visitor analytics, advertising, cross-service profiling or a public leaderboard. There is no automatic habit-expiry policy enabled.

Menu → Export → Export JSON downloads active habits, their records/notes, account email and export timestamp. It excludes archived/soft-deleted habits, account settings/credentials and separately stored note-image bytes. Import → select JSON → cloud-upload button → Yes imported a fictional active habit into a second native account, preserving the completion. New imported habits receive `(imported)`; matching IDs can merge records. An import is not full-account replacement. Native CSV import exists in source but was not tested; no CSV export is claimed.

Native authenticated `GET /api/v1/habits/export` returns the raw habit-list dictionary, including archive status; it still omits database image blobs and account configuration. API-token values must remain private. A full native UI account backup is not implied by this endpoint. The fictional GUI export/import and operator database restore are separate tests.

The per-habit trash button first archives an active habit, then soft-deletes an archived habit after confirmation; those UI actions retain the record in the habit dictionary. The native API's DELETE removes an item from the list. Account deletion is Export → Delete → Yes; the native flow first downloads the active-only JSON, then deletes the native account. Revoke any API token first through API Token → Delete. Native ORM deletion removes its habit list, settings and note-image rows; standalone API-token rows are not a cascade relationship, so prior explicit token revocation is the documented path. A deleted user's token cannot authenticate even if an orphan row remained. Session files, logs, backups and independent copies are separate, and deleting an account does not erase them instantly.

## Logs, caching and recovery

Local gateway access logging is off. Native warning/error logs and system/security logs remain and can include account identifiers or paths on failures; this is not a no-logs claim. Docker rotates 1 MiB per file, two files/container, by size rather than a fixed age. Native/private responses use no-store, while static resources keep useful one-hour caching. Edge/provider retention is not inferred from these app settings.

`backup.py` briefly pauses only this app and copies SQLite/WAL/SHM/journal, NiceGUI session files and private configuration, then always unpauses. Root-private backups live under `/opt/utilibre/beaverhabits/backups`; the daily timer is 05:20 UTC plus up to 15 minutes. **No automatic pruning is configured.** Existing retention remains unchanged. Copies may contain deleted records and secrets, remain on this VM and do not establish off-host disaster recovery.

The same pinned native image started from a copied backup with `--network none` and served the fictional habit, completion and tags. The test also removed the imported copy only in the isolated restore and verified the other user's independent copy remained. Forged trusted-email headers and unapproved anonymous/ordinary-user registration were rejected. The restore fixture was removed afterward, while the backup was retained. For recovery, stop only this app, retain the current complete state, restore database/session/config together with appropriate ownership, then use a compatible image and check native login/data before reopening. Do not overwrite production state as a verification test.
