# ZipCaptions — local-only eligibility check, 2026-10-09

Not deployed. Original upstream `jptrsn/zip-captions`, inspected commit `7e0f8a49c06e2bf83175e2a7724ec6dd8974ac72`, package 0.4.0, GPL-3.0-only. Checkout `/opt/utilibre/src/zip-captions`. No microphone recordings, accounts, tokens or real transcripts were used.

The default engine in `packages/client/src/app/modules/media/services/web-recognition.service.ts` constructs `webkitSpeechRecognition` and calls `start()` without setting `processLocally`. Browser Web Speech is **not proof of local processing**. The other native provider is Azure (`azure-recognition.service.ts` and the server's `/azure-stt` token/account modules). There is no existing native deployment flag enforcing on-device-only speech. Installing the stock static bundle would therefore leave an undisclosed external audio-processing path and does not meet this deployment's privacy requirement. Whisper was not enabled.

A narrow local-only adaptation would need a verified on-device engine and language-pack flow, explicit feature detection, fail-closed behavior before microphone capture, no Azure fallback, accurate missing-language errors, and tests with fictional spoken audio. Simply assigning an unrecognized JavaScript property is insufficient on older browsers. The available Chromium 151.0.7922.34 exposes `processLocally`, `available()` and `install()`; its `available({langs:['en-US'],processLocally:true})` call initially crashed the headless-shell renderer in this environment. A subsequent capability-only probe completed. No local transcription was performed or represented as tested. This environment result does not establish that all user browsers fail.

Additional stock behavior requiring correction before any eligible launch: Google font CSS in `styles.scss`; external upstream privacy/cookie routes; authentication, server transcript/broadcast and Azure-account dependencies; native recognition logs; and backend/signal endpoints whose configured storage/retention would need verification. Existing SRT/VTT/transcript functionality does not make the recognition provider local. Do not enable a paid provider or new recognition backend implicitly.

Exact outstanding condition: a functioning, tested local-only recognition path using native browser support or an upstream-supported FOSS engine, without a broad custom speech application. There is no public hostname, container, copied stock bundle, new collection or pending Caddy change for this candidate. Source remains available for a future narrow upstream-supported implementation.

Primary references checked: [upstream](https://github.com/jptrsn/zip-captions), [SpeechRecognition processLocally semantics](https://developer.mozilla.org/en-US/docs/Web/API/SpeechRecognition/processLocally), [on-device availability API](https://developer.mozilla.org/en-US/docs/Web/API/SpeechRecognition/available_static). The API defaults permit local or remote processing; the local requirement must be explicit and supported.

## Second implementation attempt, 03:00 UTC

The earlier shell crash is **not the current blocker**. The new reproducible probe at `deployment/evaluation/zipcaptions/check-local-recognition.mjs` ran in a separate Linux network namespace with only loopback enabled. It tested full Chromium 151.0.7922.34 in both headless and Xvfb-headed modes, with an owned fictional HTTPS fixture, all page requests intercepted and no microphone calls. Native `SpeechRecognition.available({langs:[...],processLocally:true})` returned `downloadable` for en-US and es-ES in both modes. A user-click invocation of native `install()` returned false while OS egress was disabled. There was no remote fallback, transcript or downloaded engine. Private reports: `/opt/utilibre/reports/zipcaptions-recheck-20261009/{full-headless,full-headed}.json`.

This establishes that native feature detection and a fail-closed language-pack prerequisite are feasible; it does not establish transcription quality, successful speech recognition or a permitted engine distribution. Chromium's BSD-licensed SODA wrapper/source references are not a licence grant for the downloaded engine or language-pack artifacts. The reviewed [SODA integration record](https://chromium.googlesource.com/chromium/src/+/7873e726c1fbd05ecca345113765e697c009ef03) identifies an internal implementation; the [current SODA interface](https://github.com/chromium/chromium/blob/main/chrome/services/speech/soda/soda_client.h) is only an interface. No verified FOSS grant/source for the required runtime and packs was found. No claim that every browser's local engine has the same licence is made.

Upstream was checked again: active `develop` remains 7e0f8a49c06e2bf83175e2a7724ec6dd8974ac72; `main` is b82ab581f194c34058bad63ec82568b440ff4a3f. The actual upstream `feature/webgpu` branch is f942439c4c0db7efd907e73cb67018f89e60f1d9, dated 2024-08-07. It adds `WebgpuWhisperService` and onnx-community/whisper-base through Transformers.js. That is an old Whisper experiment, not a current supported non-Whisper provider, and it was not enabled under the explicit no-Whisper requirement.

A production patch must also prevent microphone capture **before** checking availability: the native MediaService calls getUserMedia separately from WebRecognitionService. Patching only recognition.start would be incomplete. No broad replacement speech backend was built. The precise unresolved prerequisite is a supported, working FOSS local speech engine plus language packs, with their actual grants verified. Once supplied, the small application gate and existing engine selector can be adapted and tested with fictional spoken audio. Until then, publishing a caption interface that cannot meet that prerequisite would not constitute a functioning installation.
