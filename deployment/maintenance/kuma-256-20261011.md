# Uptime Kuma 2.5.6 security release

Uptime Kuma 2.5.6 is deployed. Its isolated database restore, operator sign-in,
status-page and average-response badge checks passed before release. The live
image is healthy and its public status page passed the Chromium entry check at
21:07 UTC on 11 October. Monitor definitions and access policy were preserved.
See `kuma-256-20261011.json` for exact tested identities and check boundaries.

## Upstream and local changes

The [official 2.5.6 release](https://github.com/louislam/uptime-kuma/releases/tag/2.5.6),
published 9 October 2026 and checked 11 October, fixes the average-response badge
calculation and updates runtime dependencies. The complete official MIT-licensed
slim application is used, not a reconstructed application server.

`Dockerfile.kuma-256-security` pins its Linux AMD64 upstream manifest and builder
images. It preserves the official native application, assets, entrypoint,
SQLite addon, ports and healthcheck interface. It adds:

- Signed Debian vendor updates, including OpenSSL 3.0.22, expat's Debian u4,
  Python 3.11's Debian u9, curl's Debian u15 and PCRE2's Debian u2 packages.
- Node 22.23.2 and the unchanged native healthcheck source rebuilt with Go 1.26.9.
- Locked protobufjs 7.6.6, tar 7.5.21, @grpc/grpc-js 1.14.5 and qs 6.16.0.
  The actual official image still has root qs 6.14.2, despite other updated
  copies in its dependency graph. npm's separately installed tar is patched too.

The already fixed native proxy-addr 2.0.8, express 4.22.3, body-parser 1.20.8
and engine.io 6.6.10 are retained and checked. Complete replacement package
directories replace old package records; only their dependency lookup uses a
link to the reviewed lock tree. No compiled browser bundle replacement or
exhaustive unsafe-input coverage is claimed.

Build-time package downloads use the official registry and signed vendor
repositories. They do not add visitor telemetry. Existing `checkUpdate=false`
and `checkBeta=false` settings remain in the restored native database. Existing
access restrictions, notification transports, monitor privacy, retention and
saved account data are unchanged. The slim build remains appropriate to this
installation's 59 HTTP and one TCP monitor definitions; other monitor engines
are outside this gate.

## Rebuild and isolated verification

Run from the repository root, serially, with at least 8 GiB disk headroom.
The Go build caps its parallelism at two and heap target at 2 GiB. Native test
containers use one CPU, 512 MiB and no network. The 11 October build left about
9.5 GiB free; this is an observation, not a future capacity guarantee.

```sh
docker build -f deployment/maintenance/Dockerfile.kuma-256-security \
  -t utilibre-kuma:2.5.6-security-20261011 deployment/maintenance
docker run --rm -i --name maintenance-kuma-256-libraries --network none \
  --memory 512m --cpus 1 --cap-drop ALL --security-opt no-new-privileges \
  --tmpfs /tmp --entrypoint node utilibre-kuma:2.5.6-security-20261011 - \
  < deployment/maintenance/check-kuma-libraries.cjs
docker run --rm -i --name maintenance-kuma-256-parser --network none \
  --memory 512m --cpus 1 --cap-drop ALL --security-opt no-new-privileges \
  --entrypoint node utilibre-kuma:2.5.6-security-20261011 - \
  < deployment/maintenance/check-kuma-256.cjs
KUMA_CHECK_IMAGE=utilibre-kuma:2.5.6-security-20261011 \
  python3 deployment/maintenance/check-kuma-slim.py
node deployment/maintenance/check-kuma-256-badge.mjs
```

The npm lock is exact. The Debian update intentionally consumes currently signed
vendor security packages; a future rebuild can resolve newer packages and is
not guaranteed byte-identical. Compare the resulting image identity, rerun the
native gates and scan it before changing the release pin. Do not silently
replace the tested image under the same release tag in production.

The SQLite checker uses the database's native backup API and disables polling
only in its disposable copy. The badge checker reuses that copy after verifying
all cloned monitors are disabled. Credentials pass through private stdin, not
command arguments or the public receipt. Clone databases and raw scans stay in
`/var/lib/utilibre-maintenance/kuma-256-20261011/`, outside Git.

Verified on 11 October 2026:

- 21:03:24 UTC: native 2.5.5-to-2.5.6 restored status page and operator sign-in.
- Native SQLite addon loading, protobuf UTF-8 encode/decode, Kuma's gRPC service
  construction, tar creation/extraction and qs nested-value round-trip passed.
  A representative prototype-property input did not modify object prototypes.
- 21:05:20 UTC: public average-response badge returned SVG/200; an unknown
  monitor returned N/A; an invalid monitor identifier returned native HTTP 403.
- 21:07:09 UTC release receipt: exact running image matched, native health was
  healthy, and the public status page returned HTTP 200 with no Chromium page
  errors. This was an unauthenticated desktop entry-page check, not a new
  production operator login or a long-term uptime measurement.
- Post-release access recheck: public dashboard, setup and administrative
  Socket.IO routes returned 404; a status API POST returned 405. The native
  administrative listener remains loopback-only. An isolated native notification
  template accepted an ordinary variable and rejected render/include/layout
  attempts against a synthetic file outside its template root.
- Script syntax and whitespace checks passed. Real-phone coverage, every
  notification transport, sustained uptime and load capacity were not tested.

## Security findings still open

The same cached Trivy database and complete target-image checks recorded
15 critical / 250 high occurrences in the official 2.5.6 slim image and
4 critical / 122 high in the candidate. Counts are package occurrences, not
confirmed exploitation or distinct service flaws. No findings were suppressed.

The candidate's Debian packages retain 4 critical / 90 high occurrences without
a vendor fixed version in that scan. Critical records concern libsqlite3 and
sqlite3 (`CVE-2025-7458`), python3-jwt (`CVE-2026-102267`) and zlib
(`CVE-2023-45853`). Native JavaScript dependencies retain 28 high occurrences;
the bundled, unused cloudflared binary retains four high findings. The rebuilt
native Go healthcheck has no findings in this scan. These remain review items;
an unused feature is not a patched dependency.

## Release and rollback

The coordinating maintainer updated the community Compose image pin and
recreated only the relevant service. Its pre-upgrade native SQLite backup is
`/opt/utilibre/community-backups/2026-10-11T21-05-12-712Z/kuma.sqlite`; it remains
private. Live release evidence is in
`/var/lib/utilibre-maintenance/library-release-20261011/live.json`.
Repeat the native backup and isolated gates for future upgrades; the clone
result does not replace live verification.

Previous application image:
`utilibre-kuma:runtime-security-20261011-p5`, immutable Docker image identity
`sha256:4ddf4658edd048a10fe465c92ac80561c0745071596c49a7533fd0dcc5a7aff9`.
Revert only the Kuma image if compatibility permits; preserve the data volume.
Do not assume a database downgrade is supported. If a migration requires data
recovery, stop only Kuma and restore its separately retained pre-release native
backup after reviewing the effect on monitoring changes made since release.
Never delete its volume or restore old data over a running service.
